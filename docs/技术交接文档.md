## 1. 项目定位

`MinecraftModsCloudSync`（界面名「Minecraft 模组云端同步」）是一套 **Windows 桌面双端工具**，用来在 Minecraft 服务器的**维护者**与**玩家**之间同步模组、资源包、配置等文件。

它由两个独立可执行程序组成：

| 程序 | 入口 | 面向 | 主要职责 |
| --- | --- | --- | --- |
| 服务端工具 `MinecraftSyncServer.exe` | `entry_server.py` | 服务器维护者 | 管理服务器文件仓库；把本地新客户端内容同步上服务器；检测服务器改动并发布待办；导出客户端配置；C2C 定向发包；管理共享下载区；查看日志 |
| 客户端 `MinecraftSyncClient.exe` | `entry_client.py` | 玩家 | 导入服务器下发的配置文件；定期检查并应用服务端待办；自动同步（免待办直连拉取）；下载共享文件；上报/展示更新状态 |

两端之间**没有自建后端服务**：所有交换都发生在维护者提供的 SFTP 服务器上，以「目录 + JSON 清单 + 文件」的形式完成。SFTP 主机、端口、账号、密码由服务端工具导出到加密配置文件中，客户端导入后使用。

### 1.1 代码中体现出的设计取向

这些是现有实现中反复出现、可以直接观察到的取舍，供接手时理解代码风格：

- **文件系统即协议**。不引入数据库、消息队列或额外守护进程；状态以 JSON 清单和快照文件落盘，任何一方都可以用普通 SFTP 客户端查看和备份。
- **双条件判定**。判断两个文件是否相同统一使用「大小 + 哈希」，避免「大小相同但内容被替换」的漏检；哈希算法为 MD5，仅用于变更检测，不承担安全职责。
- **快照作为记忆**。差异检测没有逐文件持久化数据库，而是把「某时刻整棵文件树的 `{相对路径: 大小/哈希}`」写成快照；对比 = 新结果 vs 快照。
- **人工判断优先于自动判断**。发送目标存在明确优先级：手动标注 > 环境检测自动纠正 > 结构性自动判定；界面同时保留「恢复自动标注」。
- **破坏性操作多重防护**。服务端根目录顶层文件在扫描、改名匹配、勾选联动、执行四层都被拦截；SFTP 删除层还有根路径拒绝。
- **可诊断优先**。网络与文件操作统一在线程中执行，日志按客户端/服务端隔离，客户端日志对 SFTP 细节脱敏。

## 2. 技术栈与运行形态

| 层 | 选型 | 说明 |
| --- | --- | --- |
| 语言 | Python 3 | 源码以 `# -*- coding: utf-8 -*-` 组织 |
| GUI | PySide6（Qt 6） | `QMainWindow`、`QTreeWidget`、`QThread`/`Signal` |
| 远程文件 | paramiko | SFTP 会话封装在 `app_common/sftp.py` |
| 加密 | cryptography（Fernet / PBKDF2-HMAC-SHA256） | 配置文件与共享文件加密 |
| Markdown 渲染 | `markdown` | 更新日志在更新对话框中渲染为富文本 |
| Windows 通知 | `winotify`（可选） | 失败时回退到 `QSystemTrayIcon` 气泡 |
| 打包 | PyInstaller | `--onefile --noconsole` |
| 安装包 | Inno Setup 6/7 | `installer/setup.iss` |
| 图标 | Pillow（`tools/make_icon.py`） | 生成 ico 并以 base64 内嵌 |

### 2.1 运行形态

- 打包结果为**单文件 exe**，运行时不依赖外部 Python 环境。
- 图标以 base64 内嵌（`app_common/icons_data.py`），运行时不需要外部素材文件；`mcmod.buf` 通过 `--add-data` 打进包内，运行时从 `sys._MEIPASS/app_common/data/` 读取。
- 启动方式：
  - 正常启动：显示主窗口（最大化）。
  - `--tray`：直接进入系统托盘（安装包的「开机自启」注册的就是带 `--tray` 的命令行）。
- 单实例：Windows 命名互斥量（`app_common/single_instance.py`，`CreateMutexW`）。第二次启动不会开出第二个进程，而是通过自定义窗口消息唤起已有窗口。
- 数据目录默认位于 exe 同级的隐藏文件夹 `.mc-sync-data`，不写 C 盘用户目录；仅当安装目录不可写时回退到 `%LOCALAPPDATA%`。

## 4. 核心概念与术语

### 4.1 三种同步方向

| 缩写 | 全称 | 数据流向 | 载体 |
| --- | --- | --- | --- |
| **C2S** | Client → Server | 本地新客户端目录 → 服务器文件仓库 | 服务端工具「更新服务端」页直接 SFTP 上传 |
| **S2C** | Server → Client | 服务器文件仓库 → 玩家游戏目录 | `{todo_dir}/manifest.json` + `{files_dir}` |
| **C2C** | Client → Client（本地对本地） | 服务端工具的本地目录 → 指定玩家的游戏目录 | `{c2c_dir}/manifests/{client_uuid}.json` + `{c2c_dir}/files/{client_uuid}/` |

三者的共同点：任务驱动、保持相对路径、以 JSON 清单描述动作。S2C 与 C2C 复用同一个 `TodoManifest` 结构。

### 4.2 服务器上的四个角色目录

| 配置项 | 默认值 | 含义 |
| --- | --- | --- |
| `server_root` | `/` | 服务端文件仓库根目录（Minecraft 服务端实际运行目录） |
| `files_dir` | `/client_files` | 面向客户端的文件仓库（S2C 下载源） |
| `todo_dir` | `/todo` | 待办清单目录，客户端读取 `{todo_dir}/manifest.json` |
| `c2c_dir` | `/c2c` | C2C 发布根目录，内含 `roster.json`、`files/`、`manifests/`、`.upload_files/` |

这些路径在 `ServerConfig` 中统一规范化为绝对路径（以 `/` 开头）；旧版相对路径配置会被自动补 `/`。导出给客户端的 `.mcscf` 中携带的是规范化后的路径。

### 4.3 快照（snapshot）

两个逻辑键：

- `repo`：服务端文件仓库的当前状态，用作「更新服务端」的对比基线。
- `publish`：上一次发布待办时的服务端文件仓库状态，用作「发布待办」的改动检测基线。

存储位置：`{数据目录}/config/snapshots/`

- `{key}_{server_id}_latest.json`：最新快照指针。
- `{key}_{server_id}_{YYYYMMDD_HHMMSS}.json`：历史快照，最多保留 40 条（`_MAX_HISTORY = 40`），超出删除最旧。

快照内容为 `{"saved_at": "...", "files": {相对路径: {"size": int, "hash": str|null}}}`。`normalize_files()` 兼容旧版「值为整数大小」的快照。

历史快照在界面上可用于查看树状结构，也可以把某个历史快照设为发布基线，从而把客户端的更新状态「回退」到那个时间点。

### 4.4 差异状态

C2S 差异树与 S2C 检测共用一套状态语汇：

| 状态 | 含义 | 默认是否勾选 |
| --- | --- | --- |
| `new` | 本地有、服务端约定位置没有 → 需要上传 | 是（`server` 以外默认勾选） |
| `update` | 两侧都有但大小不同，或大小相同哈希不同 → 需要替换 | 是 |
| `rename` | 本地新增文件与服务端独有文件大小+哈希一致 → 视为改名 | 是 |
| `obsolete` | 本地 `mods/` 中存在同一模组标识的新版，服务端残留旧版 jar | 是 |
| `server` | 服务端独有、本地没有 → 发送后会删除 | 否（默认不勾选） |
| `same` / `None` | 目标位置存在且内容一致 | 不显示 |

### 4.5 发送目标（target）

| 值 | 含义 |
| --- | --- |
| `both` | 双端：服务端 `server_root` 与客户端 `files_dir` 各放一份 |
| `server` | 仅服务端 |
| `client` | 仅客户端文件仓库（`files_dir`，C2S 扫描中键名带 `client_files/` 前缀） |
| `skip` | 跳过：扫描阶段就排除，不读、不哈希、不对比、不显示 |

`TARGET_LABELS` 对应界面中文：双端 / 服务端 / 客户端 / 跳过。

### 4.6 同步范围（sync_scope）

`ServerConfig.sync_scope` 是一个相对客户端根目录的路径列表（文件夹或文件），持久化在 `remote.sync_scope`。

- 列表为空 → 全量同步（整个客户端目录 ↔ 服务器仓库）。
- 列表非空 → 只扫描、只对比这些路径；范围外的本地文件不读、不算哈希，范围外的服务端位置也不列举。
- 快照更新时使用 `update_snapshot_scoped()`：只替换范围覆盖到的条目，范围外的旧记录保留（因为「发布待办」会复用 `repo` 快照里的 `client_files/` 读数）。

它和 `skip` 是两套机制：

- `sync_scope` 是白名单，决定「看哪些」。
- `skip` 是黑名单标注，决定「哪些完全不参与」。标注为 `skip` 的顶层目录会被并入扫描排除集合（`excludes`），文件级 `skip` 在本地收集与服务端结果兜底过滤时排除。

### 4.7 环境分析

`mod_env.py` 把「模组运行环境」与「发给谁」拆成两个维度：

- 运行环境是模组固有属性：客户端侧与服务端侧各自独立取 `required` / `optional` / `none` / `unknown`。
- 「发给谁」由 `env_target()` 结合两个开关决定：
  - `env_client_optional`：客户端侧可选的模组是否也发给客户端。
  - `env_server_optional`：服务端侧可选的模组是否也发到服务端。

判定依据按优先级：

1. jar 元数据（本地）：`fabric.mod.json` / `quilt.mod.json` 的 `environment`；`mcmod.info` 的 `clientSideOnly` / `serverSideOnly`；Forge / NeoForge 的 `mods.toml` 不含环境字段时记为 `unknown`。
2. MC 百科（联网，可选）：抓取页面的运行环境标注。`env_online` 控制是否联网补齐。

`mod_version.py` 是另一个独立维度：查发布渠道（Modrinth、CurseForge 只读接口 cfwidget）判断本地文件是 `latest` / `outdated` / `ahead` / `unknown`，用于差异审核时确认「这个文件该不该删」，避免把最新版误判为旧版残留。

### 4.8 授权与身份

- `server_id`：服务器机器标识（UUID），同一服务器固定，用于识别服务器档案。
- `client_id`：每份导出配置自动生成的客户端标识（UUID），用于授权校验与 C2C 定向。旧版配置没有 `client_id` 时，客户端回退使用 `server_id`（`client_identity()`）。
- 授权清单：SFTP 根目录 `/license.json`，结构 `{"ids": ["..."]}`。
- 客户端每次检查/应用前都会 `verify(sftp, 身份)`；编号为空、服务器清单为空、编号不在清单中分别给出不同的 `AuthError` 文案。

### 4.9 共享下载区

目录 `{c2c_dir}/.upload_files/`，用于「服务端放文件、客户端凭密码/时限下载」：

- `manifest.json` 记录每个文件的 `size` / `hash` / `encrypted` / `salt` / `created_at` / `expires_at`。
- 上传时可设置密码：内容经「密码 + 16 字节随机盐 → PBKDF2-HMAC-SHA256（200,000 次）→ Fernet」加密后存储。
- 可设置保留小时数；过期条目由服务端工具的 `cleanup_expired` 清理，客户端下载时也会拒绝已过期条目。
- 保持相对目录结构；下载到游戏目录时按同样结构落盘。

### 4.10 软件本体更新

`updater.py` 负责「工具自身」的升级，与业务同步无关：

- 查询 Gitee / GitHub Release，寻找文件名以 `MinecraftModsCloudSync_Setup_` 开头、以 `.exe` 结尾的资产。
- 下载安装包并启动 Inno Setup 安装程序，由安装程序自行请求管理员权限。
- 本地记录已提示过的版本，避免每次启动重复打扰。
- 详见第 15 章。

### 4.11 自动同步策略（免待办）

`app_common/auto_sync.py` 提供第三种同步方式：客户端不读待办清单，而是读取服务器下发的策略文件 `{todo_dir}/auto_sync.json`，直接对比 `{files_dir}` 与本地游戏目录并下载差异。

策略结构（`normalize_policy()` 规范化）：

| 字段 | 含义 |
| --- | --- |
| `enabled` | 服务端总开关；关闭时客户端不执行 |
| `include` | 白名单：目录前缀或 glob 路径；**空 = 不同步任何文件** |
| `exclude` | 黑名单：优先级高于白名单；不带 `/` 的 glob 按文件名匹配任意层级 |
| `note` / `updated_at` | 备注与下发时间 |

两层开关：服务端策略 `enabled` + 客户端 `auto_sync_enabled`，同时打开才生效。客户端**只下载、不删除**本地文件；本地多余文件作为 `extras` 只报告。相对路径以 `{files_dir}` / 本地游戏根目录为基准。

## 5. 服务器上的数据布局

以默认配置为例（`server_root = /`、`files_dir = /client_files`、`todo_dir = /todo`、`c2c_dir = /c2c`）：

```
/                                   # server_root：服务端实际运行目录
├─ start.sh                         # 顶层文件受四层防护，不会被同步删除
├─ server.properties
├─ eula.txt
├─ mods/                            # 服务端模组
├─ config/
├─ lib/                             # 服务端依赖（顶层目录，不参与删除）
├─ neoforge-xxx.jar
├─ client_files/                    # files_dir：面向客户端的文件仓库
│  ├─ mods/                         # 客户端模组
│  ├─ resourcepacks/
│  └─ config/
├─ todo/
│  ├─ manifest.json                 # S2C 待办清单
│  └─ auto_sync.json                # 自动同步策略（免待办，服务端下发）
├─ c2c/
│  ├─ roster.json                   # 服务端代号名单
│  ├─ files/{client_uuid}/...       # C2C 定向文件，保持相对结构
│  ├─ manifests/{client_uuid}.json  # 每个客户端的 C2C 清单
│  └─ .upload_files/                # 临时共享下载区
│     ├─ manifest.json
│     └─ ...
└─ license.json                     # 授权编号清单（固定根目录）
```

说明：

- `files_dir` 可以位于 `server_root` 之外的任意绝对路径。若它位于 `server_root` 之下，C2S 扫描会自动剔除重叠前缀，避免同一文件被计两次。
- 根目录扫描时，`sftp.py` 的 `SYSTEM_ROOT_DIRS`（`proc`、`sys`、`dev`、`usr`、`var`、`lib` 等）会被跳过，避免把整个 Linux 根文件系统翻一遍。
- `license.json` 固定位于 `/license.json`（`LICENSE_REMOTE_PATH`），不随 `server_root` 改变。

## 6. 服务端工作流

### 6.1 启动与多服务器管理

`ServerConfig` 的数据结构是 `{"servers": [...], "current_id": "...", "window": {...}, "auto_update_check": bool, "theme": "system"}`。

- 每台服务器是一个字典：`id`、`name`、`sftp`、`remote`、`local_mc_dir`、`sync`、`export`。
- 旧版单服务器配置（顶层 `sftp` / `remote` / `local_mc_dir` / `sync` / `export`）会在首次加载时自动迁移为 `servers[0]`。
- 所有页面通过 `config.sftp` / `config.remote` / `config.local_mc_dir` 等属性读写，属性内部始终作用于「当前选中的服务器」，因此切换服务器不需要页面自己处理。
- 服务器列表支持搜索、多选、反选、重命名、移除；拖入 `.minecraft`、`versions`、版本目录或启动器快捷方式会由 `launcher.resolve_dropped()` 识别并入库。

### 6.2 更新服务端（C2S）

页面：`server_app/ui/remote_page.py`，标签名「更新服务端（C2S）」。

#### 6.2.1 触发与线程

- 进入页面、上传完成、手动点击「重新扫描」都会触发 `_auto_detect()`。
- 扫描在 `Worker`（`QThread`）中执行，函数为 `_snapshot_scan_worker()`，主线程只更新进度文本与结果。

#### 6.2.2 扫描阶段

1. 读取本地客户端根目录 `local_mc_dir`（`_collect_local()`）。被 `skip` 的文件在这里就不读取、不算哈希。
2. 读取服务端：
   - 若设置了同步范围：对每个范围条目调用 `_scan_remote_entry()`，只列对应位置。
   - 若为全量：分别递归 `server_root` 与 `files_dir`；`files_dir` 的内容统一加上 `client_files/` 前缀并入同一键空间；若 `files_dir` 位于 `server_root` 之下，剔除重叠前缀。
3. 记录 `server_root` 下**实际存在的顶层目录名**（`_server_dirs`），供自动目标判定使用；目录列表读取失败时 `_server_dirs_ok = False`，自动目标保守按 `both`，并在状态栏提示。
4. 按需计算远程哈希（`_fill_remote_hashes()`）：
   - 「本地与远程大小相同」的候选总是重新确认，防止服务端文件被替换但大小不变。
   - 「本地新增 ↔ 远程独有」的改名候选也计算，用于改名配对。
   - 哈希通过 `hash_remote_parallel()`，优先 `check-file` 扩展。

#### 6.2.3 差异判定

对每个本地文件：

1. 计算有效目标（见 6.2.5）。若为 `skip`，直接跳过。
2. 根据目标确定「约定位置」：
   - `client` → 只认 `client_files/{rel}`
   - `server` / `both` → 认 `{rel}`，`both` 还接受 `client_files/{rel}` 作为副本
3. `_diff_status()` 判定：
   - 所有约定位置都不存在 → `new`
   - 存在但大小不同 → `update`
   - 大小相同但双方都有哈希且不同 → `update`
   - 否则视为已同步，不显示

改名配对（`_match_renames()`）：本地新增 `Y` 与服务端独有 `X` 若大小与哈希都一致，则把 `Y` 标为 `rename`，记录 `old_rel = X`。只匹配哈希已知的服务端文件；**路径不含 `/` 的顶层文件不参与匹配**。

旧版残留（`obsolete`）与临时/备份（`junk`）：本地 `mods/` 下所有 jar（含 `.jar.disabled`）按 `mod_key()` 归一化为「模组键」——去掉 `.jar/.disabled/.bak/…` 后缀，丢弃 `neoforge/forge/fabric/quilt/neo/mc` 加载器词，遇到第一个版本段（`2.6.2`、`2.6.2b`、`v1.8.17`…）截断，剩余词只保留字母数字并转小写。服务端仓库 `mods/…` 与客户端文件目录 `client_files/mods/…` 下，与本地模组键相同但**文件名不在本地**的 jar 标为 `obsolete`；文件名命中 `.bak/.temp/.tmp/.new/.old` 或 `.disabled.<数字>` 的标为 `junk`。两者都默认勾选删除，覆盖「改名换版本」与「临时文件堆积」两类残留。本地扫描会跳过 `junk` 文件（不参与同步）。

服务端独有（`server`）：快照中存在、本地不存在、且未被改名配对/旧版残留占用的条目。排除规则：

- `client_files/` 下的条目若对应本地同路径存在，视为已同步。
- **路径不含 `/` 的顶层文件与顶层目录整体不列入差异列表**。这是对 `start.sh`、`server.properties`、`eula.txt`、`lib`、`neoforge-*` 等核心文件的保护。
- 标注为 `skip` 的条目也不显示。

#### 6.2.4 差异树

9 列：文件/文件夹、状态、目标、大小、类型、时间、分析结果、最新版本、联网核对。行数据（`Qt.UserRole`）包含 `rel`、`status`、`size`、`remote_size`、`mtime`、`target`、`manual`、`checked`，改名行额外有 `old_rel`。

联网核对（可选，`_online_verify()`）：把差异列表里的 `obsolete` / `junk` / `server` 条目交给 `mod_online.verify()`，在后台线程里按本地模组的显示名 / modid / 百科 slug 解析发布渠道项目，取回项目全部版本的文件名列表后：

- 文件名精确命中项目文件列表（或按加载器/游戏版本消歧后的模糊命中，兼容手动改名）→ 按发布时间（优先）/ 版本号比较，标 `older` / `newer` / `same`；
- `newer` 表示服务端那份比本地新，**自动取消勾选**，避免删掉后玩家降级；`older` 保持原勾选；
- 「服务端独有」文件若被确认属于本地已有模组项目，改判为 `obsolete` 并追加到列表（默认不勾选，供人工核对）；
- 渠道文件列表里没有该文件名 → `unknown`（未收录），不改变勾选；断网 / 超时同样只降级为 `unknown`。
- 缓存落盘 `config_dir()/mod_online_cache.json`（默认 7 天）；整体预算 240 秒、最多 400 个本地模组、并发 8（限速 ~3.8 次/秒），超时保留已完成结果，下次核对按缓存增量继续。

默认勾选规则：`status != "server"` 的行默认勾选（`junk` 也默认勾选清理）；`server` 行默认不勾选。

#### 6.2.5 目标判定优先级

`_effective_target(rel)` 返回 `(target, manual)`，优先级从高到低：

1. **手动标注**（`remote.target_overrides`，持久化）：文件路径精确匹配优先，其次文件夹前缀（最长前缀优先）。
2. **发送前环境检测的自动纠正**（`remote.auto_targets`，持久化）：同样支持精确匹配与前缀。
3. **结构性自动判定**（`_auto_target_of`）：
   - 根目录散文件 → `both`
   - `mods/*.jar` 命中 `client_mods` 关键词 → `client`，否则 `both`
   - 其他文件：顶层目录在服务端 `server_root` 中实际存在 → `both`；服务端没有该目录 → `client`（不在服务端凭空建目录）
   - 服务端目录列表读取失败 → 保守 `both`

「分析模组环境」的结果先只显示在「分析结果」列；用户点「全部应用」后才写入手动标注。

#### 6.2.6 发送执行

`_collect_actions()` 遍历差异树，只收集被勾选的文件：

- `new` / `update` → `uploads.append((rel, target))`
- `rename` → 上传新文件；旧文件进入删除列表（`client_files/` 下的旧路径进入 `deletes_client`，否则进入 `deletes`）
- `server` / `obsolete` / `junk` → 删除（同样按前缀分到 `deletes` / `deletes_client`）

`_send_worker()` 执行：

- 上传：`target=both` 时对 `server_root` 与 `files_dir` 各上传一次；`server` 只传 `server_root`；`client` 只传 `files_dir`。
- 删除：`deletes` 删除 `server_root` 下路径，`deletes_client` 删除 `files_dir` 下路径；目录用 `delete_dir`，文件用 `delete`。
- **执行层硬拦截**：删除路径不含 `/` 时记日志并跳过，不调用 SFTP 删除。
- **历史版本**：开启 `remote.history_enabled` 后，删除前、以及覆盖已存在的同名文件前，先用 `app_common/history.py` 的 `HistoryStore.archive()` 把旧文件移动到 `{files_dir}/.mc-sync-history/{id}/{server|client}/{rel}`（同服务器内 move，不传内容；跨文件系统失败时回退为下载 → 上传 → 删除）。归档失败会跳过该条删除/替换，绝不在没有备份时做破坏性操作。发送末尾按 `history_keep`（每条路径保留几个版本）与 `history_max_mb`（总大小上限）执行 `prune()`，并写回 `index.json`。
- 发送完成后重新扫描并更新 `repo` 快照。

真正执行前还会跑一次「发送前环境检测」（`_presend_env_worker()`），对本次要发送的 jar 再确认运行环境；必要时弹确认框让用户选择纠正或保持。

### 6.3 发布待办（S2C）

页面：`server_app/ui/todo_page.py`，标签名「发布待办（S2C）」。

#### 6.3.1 基线

- 读取 `publish` 快照作为基线（`load_snapshot(server_id, "publish")`）。
- 基线在每次「发布到服务器」成功后更新：本次发布的文件写入基线，删除的文件从基线移除。
- 基线不存在（首次发布）时按空基线对比，服务器 `client_files` 里的全部文件都会列为「新增」——这正好符合首次把整合包发给客户端的需要。

#### 6.3.2 改动检测

`_detect_changes()` / `_detect_worker()` 每次**实时读取服务器 `files_dir`（client_files）的目录树**，再与「发布基线」对比，输出 `new` / `update` / `rename` / `deleted` / `obsolete` 等条目：

- 检测不依赖本地快照：服主完全可能绕过本工具、直接通过别的 SFTP/面板往 `client_files` 里加文件，只看本地快照会漏。`repo` 快照里 `client_files/` 的哈希只当作「内容相同的提示」复用。
- 目录列表本身带「大小 + 修改时间」；与本地哈希缓存 `hash_cache_{server_id}.json` 里的 `(size, mtime)` 一致时直接复用哈希，不一致才重新计算远程哈希（`check-file` 优先，不支持时下载计算）。
- 基线里同名同大小的文件**必须**重新确认内容（大小不变但被换掉也能检出）；大小不同直接判 `update`，不算哈希。
- 新增文件只有在可能和「基线里已移除的文件」配对成改名时才计算哈希，避免首次发布时把所有文件都哈希一遍。
- 改名按大小 + 哈希配对；旧版残留按 `client_files/mods` 下的模组标识/版本段判断。
- 已标记「本次不发布」（禁用）的文件不参与检测，也不会被当成删除。

#### 6.3.3 任务生成

`_publish_worker()` 生成 `TodoManifest`：

- `version`：用户填写；默认 `hotfix-MMDD-HHMM`。若与服务器上已发布清单的版本号相同，会自动补 `-HHMMSS` 后缀，避免客户端误以为已应用过而漏掉本次更新。
- `note`：发布说明。
- `tasks`：
  - `new` / `update` → `action=install`，`target` 与 `source` 均为相对路径（源文件已经由 C2S 放在 `files_dir`，发布时不再上传）。
  - `rename` → 两条任务：`delete` 旧路径 + `install` 新路径。
  - `deleted` / `obsolete` → `action=delete`。
  - 共享下载任务 → `action=download`，`source` 指向 `.upload_files/` 下的相对路径，`target` 指向游戏目录内的目标路径。
- `settings`：来自服务器设置的「客户端软件设置下发」（`check_interval_min` / `autostart` / `notify`）。
- 每个任务可带 `optional` / `silent`，界面上可逐条禁用、启用、批注。
  - `optional`：客户端应用前可以取消勾选跳过。
  - `silent`：整批任务都带 `silent` 且没有 `optional` 时，客户端会在定时检查后**后台自动应用**（「静默下载应用」）。

#### 6.3.4 发布前核对与基线更新

- 发布前逐个核对 `new` / `update` / `rename` 的源文件：必须仍存在于服务器 `files_dir` 且大小与检测结果一致，否则中止发布并提示「重新检测」（避免客户端下载到不存在的源文件）。
- 清单写入 `{todo_dir}/manifest.json`。
- 基线更新：对本次 `new` / `update` / `rename` 的文件，重新计算远程哈希写入 `publish` 快照；`delete` 类型的条目从基线移除。被禁用的条目保持旧状态，下次仍会被检测出来。

### 6.4 导出客户端配置

页面：`server_app/ui/export_page.py`。

- 为当前服务器生成 `.mcscf`（`profile.build_profile_content()`）。
- 生成时随机产生 Fernet 密钥，把 `{"sftp": {...}}` 加密后与密钥一起写入文件；同时生成 `client_id`。
- 可批量生成多份配置（每份对应一个 `client_id`），并把这些编号同步到服务器 `/license.json`（`license.save_ids()`）。
- 界面上可设置输出目录、文件名、备注，并直接打开输出目录。

### 6.5 C2C 文件发布

页面：`server_app/ui/c2c_page.py`，数据层 `app_common/c2c.py`。

- 服务端先登记一个全局唯一的「服务端代号」到 `{c2c_dir}/roster.json`（重复代号会被拒绝）。
- 选择要发送的客户端（按 `client_id`），选择本地目录（`c2c_local_dir`）。
- `send_worker()` 对比该客户端上次的 C2C 清单（`meta.files` 中的哈希表）：
  - 新增 → `install`
  - 内容变化 → 重新 `install` 并上传
  - 内容未变 → 跳过，不重复上传
  - 本地移除但内容与某新增文件相同 → 判定改名：`delete` 旧 + `install` 新
  - 本地移除且无匹配 → `delete`
- 上传目标：`{c2c_dir}/files/{client_uuid}/{相对路径}`；清单写入 `{c2c_dir}/manifests/{client_uuid}.json`。
- 任务分类按目标路径顶层目录推断：`mods` / `resourcepacks` / `config`，否则 `other`。

### 6.6 共享下载区

页面入口在服务端工具内（C2C 相关区域），数据层 `app_common/upload_files.py`。

- 上传：`collect_upload_items()` 收集文件并保留相对结构；`upload_files()` 可选加密、可选 TTL；加密内容先写临时文件再上传，避免大文件整体常驻内存。
- 列表：`list_remote_files()` 返回 `rel`、`size`、`encrypted`、`created_at`、`expires_at`、`expired`。
- 下载：`download_file()` 校验存在性与过期时间；加密文件只有在提供同一密码时才能解密。
- 清理：`cleanup_expired()` 删除过期条目并修剪空目录。

### 6.7 自动同步策略（免待办直连拉取）

页面：`server_app/ui/auto_sync_page.py`，标签名「自动同步（免待办）」。

- 编辑并下发 `{todo_dir}/auto_sync.json`；文件不存在时界面显示默认值（关闭、空白名单），读取失败会明确提示。
- 白名单/黑名单每行一个条目；`#` 开头的行忽略；非法条目（`..`、绝对路径）在规范化时丢弃。
- 匹配语义（见 8.10）：
  - 普通目录名 = 整棵子树（如 `mods`）；普通文件路径 = 精确到该文件；
  - 带 `/` 的 glob 按整条相对路径匹配（`mods/*.jar` 只匹配一层，`mods/**/*.jar` 跨层）；
  - 不带 `/` 的 glob 按文件名匹配任意层级（`*.disabled` 命中 `mods/a.disabled`）。
- 黑名单优先；目录命中黑名单时整棵子树跳过。隐藏项、垃圾文件名与临时文件（`.tmp` / `.part` / `.crdownload` 等）在任何策略下都跳过。
- 「扫描并预览同步范围」按当前表单扫描 `{files_dir}`，显示文件数、总体积、按顶层目录统计与示例文件，不写入任何东西；保存后客户端在下一次检测时读取新策略，不会打断正在进行的同步。

## 7. 客户端工作流

### 7.1 导入服务器配置

- 支持拖入 `.mcscf`，或通过文件对话框导入。
- 解析使用 `profile.parse_profile_content()`：校验 `type == "mc_cloud_sync_profile"`、`schema == 1`、必填字段，然后解密 `encrypted_sftp`。
- 同一 `server_id` 重复导入时覆盖旧档案。
- 客户端只展示服务器名称与唯一编号，不展示 SFTP 地址、账号、密码。

### 7.2 检查更新

`engine.check_all(config, progress_cb)` 逐个服务器执行：

1. 从档案解密 SFTP 信息。
2. `verify(sftp, client_identity(profile))` 做授权校验。
3. 读取 `{todo_dir}/manifest.json`（S2C）。
4. 读取 `{c2c_dir}/manifests/{client_id}.json`（C2C）。读取失败不阻塞整体检查（C2C 属于可选功能）。
5. 记录 `last_seen_version` / `last_seen_sig` / `last_seen_c2c` 与时间。

返回结构：`{server_id: {"ok": bool, "manifest": TodoManifest|None, "c2c_manifest": TodoManifest|None, "error": str}}`。

是否算「有新更新」由 `engine.is_manifest_new(profile, manifest, c2c_manifest)` 判断：

- 版本号与 `last_applied_version` 不同 → 新更新；
- 版本号相同，但 `manifest_signature(manifest)`（版本 + 任务 + 设置的内容指纹）与 `last_applied_sig` 不同 → 也算新更新（服务端当天二次发布、版本号重复时不会漏）；
- 旧客户端配置没有 `last_applied_sig` 时退化为只比版本号。

### 7.3 应用更新

`engine.apply_update(config, profile, manifest, c2c_manifest, progress_cb, skip_optional_ids)`：

1. 校验游戏目录 `local_mc_dir` 存在。
2. `verify()` 授权。
3. 先应用 S2C 任务，再应用 C2C 任务：
   - `install`：从 `files_dir`（S2C）或 `{c2c_dir}/files/{client_id}`（C2C）下载到临时目录，再 `shutil.move` 到游戏目录对应路径。
   - `download`：从 `.upload_files` 共享区下载。
   - `delete`：删除游戏目录内对应文件（不存在则记为跳过）。
   - `optional` 且 `id` 在 `skip_optional_ids` 中 → 跳过。
   - 任何单条任务异常都记入 `summary["errors"]`，不中断其余任务。
4. 应用随待办下发的客户端设置：
   - `check_interval_min`：限制在 5–1440 分钟。
   - `autostart`：写入注册表开机自启。
   - `notify`：系统通知开关。
5. 返回 `{"installed": [], "deleted": [], "skipped": [], "errors": [], "settings": []}`。

「静默批次的自动应用」：定时检查（非手动）发现新清单、且全部任务都是 `silent`、没有 `optional` 时，客户端调用 `_start_apply(..., auto=True)` 在后台直接应用，不弹确认/进度/结果对话框；失败时只记日志并按设置发系统通知。手动检查仍走原来的确认流程。

### 7.4 定时检查与托盘

- `ClientConfig.check_interval_min` 默认 60 分钟。
- 主窗口按间隔触发检查；服务端可通过 `manifest.settings` 覆盖该值。
- 定时检查发现新更新时：普通批次只发通知提醒玩家打开客户端；静默批次在后台自动应用（见 7.3）。
- 关闭窗口最小化到托盘；`--tray` 启动直接进托盘。
- 有可应用更新时可通过 `notifications.notify()` 发系统通知。

### 7.5 自动同步（免待办直连拉取）

客户端主界面新增「自动同步」分组：

- `ClientConfig.auto_sync_enabled`（默认 `false`，本地开关）。
- `ClientConfig.auto_sync_interval_min`（默认 30，范围 5–1440）。
- 「立即检测并拉取」按钮：立即执行一次；打开开关时也会自动执行一次。
- 定时器按间隔触发；同一时刻只允许一个自动同步线程，且不会与「应用待办」同时写游戏目录。

`engine.auto_sync_run(config, profile, apply=True)`：

1. 授权校验 → `load_policy()` 读取 `{todo_dir}/auto_sync.json`。
2. 策略不存在 / 已关闭 / 白名单为空 → 返回 `skipped`（不算错误，界面给出对应提示）。
3. `plan_sync()` 扫描服务器与本地，生成下载计划（见 8.10、9.7）。
4. `apply_sync()` 逐文件下载到临时文件后 `os.replace()` 原子替换；单个失败只记入 `errors`，不中断其余文件。下载目标经 `safe_target()` 与「必须位于游戏目录内」双重校验。
5. 结果写入 `profiles[*].auto_sync_at / auto_sync_files / auto_sync_status` 供界面展示。

`AutoSyncThread` 把上述流程放到后台线程，进度通过 `progress` 信号回填状态栏。定时触发失败只记日志并按 `notify` 设置发系统通知；手动触发会弹结果汇总（含本地多余文件清单）。

由 `TodoManifest.to_dict()` 生成：


| 字段 | 类型 | 说明 |

## 9. 哈希与性能设计

### 9.1 双条件判定

统一约定：**大小不同 → 必然不同；大小相同 → 再比哈希**。哈希算法默认 MD5。

适用位置：C2S 差异判定、S2C 发布基线、C2C 差异判定、共享区清单。

### 9.2 本地哈希缓存

`file_hash.hash_file_cached()`：

- 缓存键为绝对路径，值为 `(size, mtime, hash)`。
- 只有「大小 + 修改时间」都没变才复用；文件一改动即失效。
- 上限 50000 条，超出整体清空。

用于重复扫描同一本地目录时避免把整个模组包重新读一遍。

**S2C 检测的远程哈希缓存**（`{config_dir}/snapshots/hash_cache_{server_id}.json`，由「发布待办」页维护）：

- 值：`{相对路径: {"size": int, "mtime": int, "hash": str}}`。
- 每次检测实时列 `client_files` 目录（`listdir_attr` 一次拿到大小 + 修改时间）；`(size, mtime)` 与缓存一致 → 内容没变，直接复用哈希，不再访问文件内容。
- 对不上、且基线里同名同大小的文件 → 重新计算远程哈希确认（这正是「大小不变但内容被换掉」的检出方式）。
- 缓存只记录本次仍在服务器上的文件；删除/禁用项自动剔除。

### 9.3 远程哈希

两条路径：

1. **`check-file@openssh.com` 扩展**（OpenSSH 8+）：在服务器端直接算哈希，只传回一个字符串。`remote_hash_many()` 以流水线方式一次发出多个请求再依次收响应，把逐文件的网络往返摊薄。
2. **回退下载计算**：服务器不支持该扩展时，下载到临时文件计算后删除。

`hash_remote_parallel()` 最多 4 个工作线程，每条连接内部再走批量流水线；连接数量受 `sftp` 模块的全局并发名额约束。

### 9.4 扫描缓存

`SFTPManager` 维护内存目录扫描缓存：

- 键：`(host, port, username, root, excludes, skip_system)`。
- TTL：60 秒（`_SCAN_CACHE_TTL`）。
- 任何写入型操作（上传、删除、重命名等）都会清空缓存，避免返回过期数据。

### 9.5 连接并发

`_CONN_MAX = 5`：同一进程内最多同时 5 个 SFTP 会话，用 `BoundedSemaphore` 控制。目的是适配并发连接受限的免费/小主机，避免页面自动检测、自检、并行扫描同时开太多连接被拒。

### 9.6 快照内存驻留

C2S 扫描结果在页面内以 `self._rows` 保留，排序、过滤、勾选联动都在内存中完成，不重复访问 SFTP；只有重新扫描或发送完成后才重建。

### 9.7 自动同步的哈希与回退

- 大小不同 → 直接下载，不算哈希。
- 大小相同 → 先用 `remote_hash_many()`（`check-file` 流水线）算远程哈希，与本地 `hash_file_cached()` 比对；不同才下载。
- 服务器不支持 `check-file` 时，大小相同的文件退化为「远程 mtime 比本地新 2 秒以上 → 下载」，避免为确认哈希而把整个模组包下载一遍；下载完成后把本地 mtime 对齐到服务器 mtime（`os.utime`），因此不会因两端时钟差反复下载。
- 无差异时自动同步不写任何本地文件；本地哈希缓存按 `(size, mtime)` 复用。

## 10. SFTP 接入层

`app_common/sftp.py` 的 `SFTPManager` 是唯一远程入口。

### 10.1 连接

- `connect(retries=2)`：先占用全局并发名额，再建立连接。
- 认证错误等确定性失败不重试；网络超时/拒绝等瞬时错误按递增退避重试。
- `close()` 释放名额；上下文管理器（`with SFTPManager(...) as sftp`）保证释放。
- 客户端统一使用 `sanitize_log=True`，日志与异常文本不出现地址、端口、账号。

### 10.2 目录扫描

`list_files_recursive_with_size(path, excludes=None, skip_system=False, max_workers=3, progress_cb=None)`：

- 返回 `[(相对路径, 大小)]`。
- 跳过隐藏项（以 `.` 开头）。
- `excludes` 为顶层目录名集合，忽略大小写。
- `skip_system=True` 时跳过 `SYSTEM_ROOT_DIRS`。

### 10.3 写入与删除

- `upload()` / `download()` 支持字节级进度回调。
- `mkdirs()` 递归建目录。
- `move()` 优先 `posix_rename`，失败回退 `rename`。
- `delete()` / `delete_dir()` 均调用 `_refuse_root()`：路径为空或 `/` 时抛 `SFTPError`，防止误删根目录。

### 10.4 其他

- `read_text()` / `write_text()` 用于 JSON 清单读写。
- `exists()` / `is_dir()` / `stat()` 用于存在性与类型判断。
- `join()` 统一 POSIX 风格路径拼接。

## 11. 安全设计与边界

### 11.1 传输与凭据

- 传输层为 SFTP（SSH），使用密码认证（`transport.auth_password`）。
- 服务端工具的 SFTP 凭据以明文保存在本机隐藏配置文件 `server_config.json` 中；该文件位于 `.mc-sync-data/config/`，目录带隐藏属性，卸载时可选择删除。
- 客户端不直接保存明文凭据：凭据在导入的 `.mcscf` 内容里，导入后以配置文件原文存进 `client_config.json` 的 `profiles[].content`，运行时再解密。

### 11.2 `.mcscf` 的实际保护强度

`profile.py` 的实现是：

1. `Fernet.generate_key()` 生成随机密钥。
2. 用该密钥加密 `{"sftp": {...}}`。
3. **把密钥 `key` 与密文 `encrypted_sftp` 一起写进同一个 `.mcscf` 文件**。

因此它的实际效果是「防止用文本编辑器直接读到明文密码」，**不是口令保护**：拿到 `.mcscf` 文件的人可以按同样结构解出 SFTP 凭据。分发配置文件时应按「等同于分发服务器凭据」对待。

### 11.3 授权

- `/license.json` 是服务器端的授权白名单。
- 客户端每次检查与应用都会 `verify()`；未授权会得到明确的 `AuthError` 文案。
- 授权是「编号是否在清单中」的校验，不涉及签名或证书。

### 11.4 共享文件加密

- 密码 + 16 字节随机盐 → PBKDF2-HMAC-SHA256（200,000 次）→ 32 字节 Fernet 密钥。
- 盐随清单记录，不随文件；同一文件每次上传重新生成盐。
- 未设置密码时文件以明文存储。
- 过期清理由服务端执行；客户端下载时也会拒绝 `expires_at` 已过的条目。

### 11.5 路径安全

- `tasks.safe_target()` 拒绝 `..` 与 `.` 路径段，统一把反斜杠转 `/`。
- 客户端所有任务目标都先经过 `safe_target()` 再拼接游戏目录。
- 服务端删除拒绝空路径与根路径。
- 服务端根目录顶层文件在 C2S 的扫描、改名匹配、勾选联动、执行四层均受保护。

### 11.6 日志脱敏

- 客户端 `SFTPManager(sanitize_log=True)`：连接与异常日志不输出地址、端口、凭据。
- 客户端日志目录独立（`logs/client`），服务端日志独立（`logs/server`），互不混杂。

## 12. 日志与诊断

`app_common/logger.py`：

- 日志目录：`{数据目录}/logs/client` 与 `{数据目录}/logs/server`，由 `set_app_scope()` 决定。
- 文件名：`{key}_{YYYYMMDD}.log`，按天切分。`key` 由 `set_log_context()` 设置，主窗口切换服务器时会切到对应的日志文件；未设置上下文时为 `{YYYYMMDD}.log`。
- 因此同一端在切换服务器后会产生多个日志文件，而不是单一文件。
- 单文件上限 2 MB，最多 10 份（`RotatingFileHandler`）。
- 格式：`%(asctime)s [%(levelname)s] %(name)s | %(message)s`。
- 日志器名称体现模块，例如 `client.engine`、`server.remote_page`、`sftp`、`app_config`。
- 客户端模式下 `sftp` 日志会被过滤，避免泄漏服务器细节。

日志查看：

- 服务端「日志」页（`server_app/ui/log_page.py`）：按天列表、按时间段查询、导出。
- 通用日志管理对话框（`app_common/log_manager.py`）：按时间段/关键词查看与导出。
- 配置管理对话框（`app_common/config_manager.py`）：备份/恢复隐藏的配置文件。

排查建议（属于现有工具能力，不是强制流程）：先看日志中的模块名定位到具体阶段，再结合界面状态栏的进度文本与快照的 `saved_at` 判断是扫描、对比还是执行阶段的问题。

## 15. GitHub / Gitee 发布与软件自动更新

这一章说明仓库里与「发布」相关的**现有机制**：哪些是代码自动完成的，哪些是人工在平台上完成的。

### 15.1 两个发布渠道

代码中同时存在两个远端标识，均指向 `CookieWYQ/MinecraftModsCloudSync`：

| 常量 | 值 |
| --- | --- |
| `GITHUB_REPO` | `CookieWYQ/MinecraftModsCloudSync` |
| `GITEE_REPO` | `CookieWYQ/MinecraftModsCloudSync` |
| `UPDATE_SOURCE_ORDER` | `("gitee", "github")` |

也就是说，**查询与下载的优先顺序是 Gitee 在前、GitHub 兜底**。`updater.py` 顶部的模块 docstring 只写了 GitHub，属于历史注释，实际行为以 `UPDATE_SOURCE_ORDER` 为准。

### 15.2 Release 的约定（自动更新的契约）

自动更新只认符合以下约定的资产：

- Release 的 tag 能被 `parse_version()` 解析为数字版本（如 `v1.2.13` → `(1, 2, 13)`）。
- 资产文件名以 `MinecraftModsCloudSync_Setup_` 开头，并以 `.exe` 结尾（`SETUP_PREFIX`）。
- 资产字段：
  - GitHub：`browser_download_url`
  - Gitee：兼容 `assets` 与 `attach_files` 两种命名，下载地址取 `browser_download_url` 或 `url`

版本历史列表取每个源最近 30 条（`per_page=30`），并用 `sort_releases_desc()` 统一按版本号倒序。两个平台的默认排序并不一致（GitHub 新→旧，Gitee 旧→新），排序是为了让界面上的「最新」标记正确。

### 15.3 查询接口

| 用途 | 地址 |
| --- | --- |
| GitHub 最新 Release | `https://api.github.com/repos/{GITHUB_REPO}/releases/latest` |
| GitHub 版本列表 | `https://api.github.com/repos/{GITHUB_REPO}/releases?per_page=30` |
| Gitee 最新发行版 | `https://gitee.com/api/v5/repos/{GITEE_REPO}/releases/latest` |
| Gitee 版本列表 | `https://gitee.com/api/v5/repos/{GITEE_REPO}/releases?per_page=30` |

请求头带 `User-Agent: MinecraftModsCloudSync/{APP_VERSION}`；GitHub 额外带 `Accept: application/vnd.github+json`。

`fetch_latest()` 的行为：

- 依次尝试 `UPDATE_SOURCE_ORDER` 中的源。
- 某源可用但没有安装包资产 → 跳过并记录警告。
- 全部不可达 → 抛出最后一个错误，由界面提示。

### 15.4 下载与安装

`download_setup(url, dest, progress_cb, cancelled_cb, timeout)`：

1. `_build_attempts(url)` 构造通道列表：
   - 传入 GitHub 直链时，先构造同 tag、同文件名的 Gitee 直链（国内更快），失败再回退 GitHub。
   - 传入 Gitee 直链时直接使用。
2. `_download_one()`：
   - 每次进入通道前清理 `dest` 残留，防止不同来源/不同版本的旧文件拼接导致安装包损坏。
   - 支持 `Range` 断点续传；服务器返回 `416` 时清空临时文件重新下载。
   - 处理 `206`（部分内容）与 `200`（完整内容）。
   - 最多跟随 5 次重定向（Gitee 下载会 302 到对象存储）。
   - 单通道内断线自动重试，最多 3 次（`DOWNLOAD_MAX_RETRIES`），重试不重新下载已完成字节。
   - 结束后做完整性校验（大小与预期一致）。
3. 下载完成后启动安装程序；安装程序由 Inno Setup 自行请求管理员权限。

自动检查时机：启动时 + 每 6 小时（界面层定时器），可在设置中关闭（`auto_update_check`）。

### 15.5 GitHub 发布链路的现状

仓库内与「发布」直接相关的自动化只有 Gitee 一侧：

- `build.py --gitee` 会调用 `tools/gitee_sync.py`。
- `gitee_sync.py` 的能力：
  - `sync_code()`：确保 Gitee 仓库存在（不存在则从 GitHub 导入），并触发代码同步；优先用 Gitee 官方 sync 接口，失败回退 `git push`。
  - `ensure_release()`：确保发行版存在，不存在则创建，存在则更新标题/正文。注意 Gitee 对「tag 不存在」的 GET 返回 `200 + null`，代码对此做了兼容。
  - `upload_assets()`：上传附件；上传前查询现有附件，跳过同名文件。
  - `sync_via_browser()`：Playwright 浏览器模拟模式，用于网页端「同步更新」/「从 GitHub 克隆导入」；登录态保存在本地 profile 目录。
- 令牌获取顺序：`--token` > 环境变量 `GITEE_TOKEN` > Windows 凭据管理器。可用 `--save-token` 预先保存。

**GitHub 一侧没有仓库内的发布脚本**。代码只读取 GitHub Release（查询与下载），不调用 GitHub 的创建/上传接口。现有工作流是：

1. `python build.py` 在本地生成 `release/` 三个产物。
2. 在 GitHub 上创建 tag 与 Release，上传三个附件：
   - `MinecraftSyncClient.exe`
   - `MinecraftSyncServer.exe`
   - `MinecraftModsCloudSync_Setup_<version>.exe`
3. 需要国内镜像时执行 `python build.py --gitee --gitee-body-file 版本介绍.txt`，由 `gitee_sync.py` 把同一份资产与版本说明同步到 Gitee。

这条链路的关键约束不在代码里，而在**命名约定**：自动更新只识别 `MinecraftModsCloudSync_Setup_` 前缀的 `.exe` 资产。若发布时改了安装包文件名，自动更新会认为「源可用但没有安装包」。

### 15.6 版本号从哪来

- 唯一的版本源头是 `app_common/constants.py` 的 `APP_VERSION`。
- `build.py` 用正则从该文件读取版本号，用于：
  - 安装包文件名 `MinecraftModsCloudSync_Setup_<version>.exe`
  - Inno Setup 的 `/DMyAppVersion`
  - Gitee tag（`v{version}`）
- `updater.py` 用同一个 `APP_VERSION` 作为 `User-Agent`，并用于比较远端版本与本地版本。

## 18. 已知边界与易误解点

这一节集中列出「代码现状与直觉/历史注释可能不一致」的地方，避免接手时误判。

1. **`.mcscf` 不是口令保护。**
   `profile.build_profile_content()` 把随机 Fernet 密钥和密文写在同一个文件里。它能防止直接文本读取，但拿到文件即可解密。不要把 `.mcscf` 当作「需要密码才能打开」的安全容器。

2. **自动更新源顺序是 Gitee → GitHub。**
   `updater.py` 顶部 docstring 写的是「从 GitHub Release 检测」，但 `UPDATE_SOURCE_ORDER = ("gitee", "github")`，且 `fetch_latest()` / `fetch_releases()` / `download_setup()` 都按该顺序执行。

3. **两个 exe 都不请求管理员权限。**
   `build_exe()` 支持 `--uac-admin`，但 `main()` 两次调用都是 `admin=False`。管理员权限来自 Inno Setup 安装程序（`PrivilegesRequired=admin`），不是 exe 自身。

4. **`SYNC_CATEGORIES` 目前未被使用；`DEFAULT_SYNC_EXCLUDE_PATTERNS` 已用于自动同步默认黑名单。**
   前者在 `constants.py` 中定义但扫描/对比流程没有引用；后者现在作为「自动同步策略」的默认排除项（`auto_sync.default_policy()`），C2S/S2C 实际生效的排除项仍是 `remote_page.DEFAULT_EXCLUDE`（`logs` / `cache` / `crash-reports` / `backups`）与用户配置的 `remote.exclude`。

5. **`server_app/ui/sync_page.py` 是未被装配的遗留页面。**
   `main_window.py` 导入的是 `remote_page.RemoteFilePage`、`todo_page.TodoPage` 等，没有任何模块导入 `sync_page.SyncPage`。

6. **仓库内没有 GitHub 发布脚本。**
   只有 Gitee 同步工具（`tools/gitee_sync.py`）。GitHub Release 的创建与附件上传是在平台上完成的；代码只负责读取 GitHub Release 供自动更新使用。

7. **`server_root` 默认 `/`，并且扫描会跳过系统目录。**
   这是为了避免把 Linux 根文件系统整个翻一遍。若服务端目录结构特殊（例如把服务端放在 `/home/mc/server`），应在「服务器设置」里把 `server_root` 指到实际目录，而不是依赖默认值。

8. **顶层文件保护是「不显示/不匹配/不联动/不删除」四层。**
   路径不含 `/` 的服务端独有文件不会出现在差异树里，也不会被当作改名旧文件，也不会被父节点勾选联动带上，执行删除时还会被硬拦截。这意味着「服务端根目录下的散文件」在现有实现中不参与 C2S 同步。

9. **`skip` 会改变扫描本身，而不只是隐藏。**
   标注为 `skip` 的顶层目录会并入 `excludes`，服务端扫描不递归；文件级 `skip` 在本地收集与服务端结果兜底过滤中排除。它与「同步范围」不同：范围是白名单，`skip` 是黑名单式标注。

10. **`sync_scope` 非空时不会清理范围外的快照记录。**
    `update_snapshot_scoped()` 只替换范围覆盖到的条目，范围外保留旧值。这是为了让「发布待办」继续复用 `repo` 快照里 `client_files/` 的哈希提示；如果在范围模式下发现旧记录干扰判断，应恢复全量扫描一次再缩小范围。

11. **S2C 每次检测都会实时扫描服务器 `client_files`。**
    不再只看本地 `repo` 快照——服主可能绕过本工具直接往服务器加文件，快照看不到。代价是首次检测（或缓存被清空后）需要对「基线里同名同大小」的文件各算一次远程哈希；之后靠 `hash_cache` 的 `(大小, 修改时间)` 命中，基本不再重复哈希。目录里已有的文件不会被重新下载（除服务器不支持 `check-file` 时的回退路径）。

12. **「静默下载应用」只在整批任务都静默且无可选任务时自动执行。**
    客户端定时检查发现这类批次会后台自动应用，不弹确认框；只要有一个任务不是静默、或带 `optional`，仍走玩家手动确认流程。手动检查始终走确认流程。

13. **C2C 清单读取失败不阻塞检查。**
    `check_all()` 对 C2C 读取失败只记警告，`c2c_manifest` 置 `None`。这表示「未配置 C2C」与「C2C 暂时不可用」在客户端表现一致。

14. **MD5 只用于变更检测。**
    全项目的哈希算法默认 MD5，用途是比较文件内容是否变化、配对改名、维护基线，不用于完整性签名或安全校验。

15. **`files_dir` 可以不在 `server_root` 之下。**
    扫描会自动处理重叠前缀；但如果两者是不同磁盘/不同挂载点，`files_dir` 的内容在快照中统一以 `client_files/` 前缀表示，这只是一个逻辑键，不对应 `server_root` 下的真实目录。

16. **客户端的「已知版本库」是目录识别，不是启动器集成。**
    `launcher.resolve_dropped()` 识别 `.minecraft`、`versions`、含 `{version}.json` 的版本目录、启动器快捷方式，不调用任何启动器 API。

17. **安装包卸载会询问是否删除配置与日志。**
    默认按钮是「否」（`MB_DEFBUTTON2`），保留数据便于重装后继续使用。

18. **自动同步只下载、不删除本地文件。**
    服务器上没有、本地有的文件只会以 `extras` 形式提示数量（手动检测时可查看清单），不会自动删除。需要删除客户端文件时仍应走「发布待办（S2C）」的 delete 任务。

19. **自动同步的 mtime 回退有边界。**
    服务器支持 `check-file` 时按哈希精确判断；不支持时，大小相同的文件只能靠「远程 mtime 比本地新 2 秒以上」判断。若有人以**相同大小、相同/更旧修改时间**替换服务器文件，这种替换不会被发现。需要严格保证时可改用发布待办（其哈希缓存会强制确认同名同大小文件）。

20. **自动同步与发布待办互不排斥，也不互相同步。**
    两条链路都可能写同一个游戏目录：客户端界面会避免两者同时执行，但服主若同时维护待办清单与自动同步策略，同一文件可能被两边先后覆盖（后写的生效）。建议按服务器只选一种主用方式，或让两者的范围不重叠。

21. **策略白名单为空是「不同步」，不是「全部同步」。**
    `include` 为空时客户端不会扫描/下载任何文件；服务端页在「启用但白名单为空」时会阻止保存（除非明确确认保存空白名单）。

22. **历史版本默认关闭，且历史目录本身不参与任何同步。**
    `.mc-sync-history` 位于 `{files_dir}` 下、以 `.` 开头，`list_files_recursive_with_size()` / `_scan_client_files()` / `_local_files()` 都会跳过隐藏项，因此不会被「更新服务端」「发布待办」「自动同步」扫描或下发。归档优先用服务器内 move（不传内容），只有 move 失败（跨文件系统等）才回退下载+上传；若归档失败，该条删除/替换会被跳过。历史不是「无限版本库」：默认每条路径保留 3 个、总量 512 MB，超出自动从最旧清理。

23. **C2S 只清理服务端仓库；客户端已装旧版需要 S2C 的删除任务才能移除。**
    C2S 的「旧版残留 / 临时备份」删除只作用于 `server_root/mods` 与 `client_files/mods`。客户端游戏目录里的旧 jar 不会被直接删除：需要「发布待办」检测出 `deleted` 任务并发布（依赖发布基线里存在该旧文件），或由客户端自行检测重复模组。若发布基线过期（例如很久没发布过），旧文件不在基线里，删除后不会生成客户端删除任务；此时应先重建/发布一次基线再清理，或使用客户端侧清理。

## 21. 近期改动记录（服务端发布待办 / 客户端）

记录一次针对「发布待办（S2C）」与客户端应用链路的修改（2026-11，在 1.2.13 源码上）；另新增「联网核对旧版」（`app_common/mod_online.py`）与差异列表第 9 列：

### 21.1 服务端「发布待办」

- **改动检测改为实时扫描服务器 `client_files`**，不再复用「更新服务端」页留下的本地快照。原因：服主可能绕过本工具直接往服务器加文件，快照会漏；现在打开/刷新本页都直接看服务器真实目录。
- 引入 `hash_cache_{server_id}.json`（按 `大小 + 修改时间 + 哈希`）：目录列表自带 mtime，命中即复用哈希，不重复下载；只有 mtime/size 变化或基线同名同大小需要确认时才重新算哈希。
- 新增 `TodoPage._scan_client_files()`：一次 `listdir_attr` 递归拿到大小/修改时间，隐藏项跳过。
- 发布前核对源文件仍存在且大小一致，不一致则中止并提示重新检测。
- 发布版本号与服务器上已发布清单重复时，自动补 `-HHMMSS` 后缀。
- 默认版本号从 `hotfix-MMDD` 改为 `hotfix-MMDD-HHMM`。

### 21.2 客户端

- `app_common.tasks.manifest_signature()`：清单内容指纹（版本 + 任务 + 设置）。
- `engine.is_manifest_new()`：版本号变化，或版本号相同但指纹变化 → 认为有新更新；客户端配置新增 `last_applied_sig` / `last_seen_sig`（旧配置没有时退回只比版本号）。
- `engine.is_silent_batch()` + `ClientMainWindow._auto_apply_if_possible()`：定时检查发现「整批静默、无可选任务」的清单时后台自动应用；`_start_apply(auto=True)` 不弹确认/进度/结果框，失败只记日志并按设置通知。
- 手动检查、普通批次仍走原有确认流程。

### 21.3 测试

新增 `tests/fake_sftp.py`（paramiko 本地 SFTP 服务器）与 `tests/test_e2e_sync.py`（端到端回归），覆盖：

- 仅客户端模组只进 `client_files`、服务端模组不进 `client_files`、双端两边各一份；
- 首次发布、发布后基线清空、同一版本号二次发布；
- 绕过工具直接新增/同大小替换/删除服务器文件时，S2C 仍能检测并同步到客户端；
- 发布前源文件缺失会中止；静默批次可被客户端识别。

运行：`.venv/Scripts/python.exe tests/test_e2e_sync.py`（输出 `E2E OK`）。

### 21.4 自动同步（免待办直连拉取，2026-11）

- 新增 `app_common/auto_sync.py`：策略模型、黑白名单/glob 匹配、服务器与本地扫描、对比计划、原子下载；客户端只下载不删除，本地多余文件只报告。
- 服务端新增「自动同步（免待办）」页：总开关、白名单、黑名单、备注、范围预览、下发到 `{todo_dir}/auto_sync.json`；主窗口标签页由 6 个变为 7 个。
- 客户端配置新增 `auto_sync_enabled`（默认关闭）与 `auto_sync_interval_min`（默认 30，5–1440）；`engine.auto_sync_run()` + `AutoSyncThread`；主界面新增开关、间隔、立即检测按钮与定时器。开启开关后会立即检测一次。
- 两层开关：服务端策略 `enabled` + 客户端本地开关同时打开才生效；策略缺失/关闭/空白名单会分别给出提示。
- 客户端只下载策略允许的路径；本地多出来的文件只提示，不自动删除；下载用临时文件 + `os.replace()` 原子替换。
- 新增 `tests/test_auto_sync.py`：策略下发/读取、黑白名单与 glob 语义、同大小哈希与 mtime 回退、范围外文件不被下载、本地多余文件不被删除、客户端引擎端到端、界面开关与定时器状态。

运行：`.venv/Scripts/python.exe tests/test_auto_sync.py`（输出 `AUTO SYNC OK`）。
